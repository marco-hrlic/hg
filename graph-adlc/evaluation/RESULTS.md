# graph-adlc v0.2 — Evaluation results

**Date:** 2026-11-03 · **Dataset:** 1.0 (24 scenarios) · **Oracle:** v1.0 (primary, blind) and v1.1 (after the logged post-unblinding review) · **Engine:** graph-adlc 0.1.0, unmodified · **Harness:** 0.2.0

**Bottom line:**
* On this small, synthetic, single-reviewer corpus, the v0.1 graph (B) did **not** find more required checks than a
  simple document baseline built from the same facts (A). Recall was 0.574 for B and 0.593 for A, and precision was
  similar (0.431 vs 0.457).
* Evidence-gated pruning (C) removed 6 checks. Five were unnecessary, but **one was a critical required check**, in the
  scenario built to test valid-but-incomplete evidence.
* The results **fail to support** both pre-registered hypotheses H1 and H2 on this corpus. Overall they are
  **insufficient to evaluate the original thesis**; see the limitations below.

Every number below is generated by `evaluation/run_all.sh` into `evaluation/out/`. This file only interprets them.

|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|

**Oracle v1.1** applies a logged decision for each of the 143 unlabeled predicted pairs: 137 were confirmed not

## 3. Pruning safety (B vs C)

In every scenario, C's predictions are a subset of B's, and a test checks this.

| Scenario | Evidence | Pruned (removed by C) | Oracle label | Pruning miss |
|---|---|---|---|---:|
| SC-09 retry-loop refactor | EV-1 passed, CON-IDEMPOTENCY r1, current | `CMP-REPORTING:check_contract` via E13 | not required | 0 |
| SC-10 key-helper refactor | EV-1 **failed** | nothing (correct) | — | 0 |
| SC-11 same refactor | EV-1 passed but **stale**: contract moved to r2 in setup | nothing (correct) | — | 0 |
| **SC-14** thousands separators | EV-1 passed, CON-MONEY-FORMAT r1, current; the test table had no amounts ≥ 1000 | `CMP-ORDERS:check_contract` via O20, `CMP-NOTIFIER:check_contract` via O21 | **CMP-ORDERS: required, critical**; CMP-NOTIFIER: not required | **1** |
| SC-15 formatter caching | EV-1 passed, current | `CMP-ORDERS`, `CMP-NOTIFIER` check_contract | not required (both) | 0 |
| SC-24 additive event field | EV-1 passed for CON-INVENTORY-API; hypothesized O34 present | `CMP-ORDERS:check_contract` via O18; **not** O34 (correct) | not required | 0 |

**Summary.** C removed 6 pairs (77 → 71 predicted, about −8%). 5 of them were unnecessary and 1 was a critical
miss. That cost 4 evidence records, each standing for a contract-suite run. The time to produce them was not
measured.
* The v0.1 admissibility rules behaved exactly as specified: failed, stale and bare-claim evidence did not prune,
  and the hypothesized edge was never pruned.
* SC-14 shows the gap: **admissible is not the same as sufficient.** The record was current and passing, but its
  coverage did not include the clause the consumer actually relied on.

## 5. Concrete failures with source evidence

1. **FN, critical, B and C — SC-10 `TEST-RETRY:rerun_test`.** An implementation-aspect change to `CMP-PAYMENT` yields
   only `REQ-CHARGE`/`REQ-RETRY:check_contract` (E08, E09) and a provisional `CMP-REPORTING` (E13). The rule table
   has no path from an implementation change to verifying tests. Across the 9 implementation-aspect scenarios,
   **no method emitted a single `rerun_test`**. This accounts for 12 of B's 23 misses under the v1 labeling rule.
2. **FN, critical, C only — SC-14 `CMP-ORDERS:check_contract`.** Pruned at O20 by EV-1 (`CON-MONEY-FORMAT` r1,
   passed, current). B had it. This is the valid-but-incomplete evidence case from §3.
3. **FN, critical, B and C — SC-23 `TEST-EMAIL:rerun_test`.** This is the terminal-consumer rule from probe 2:
   B's deepest path is `[O11, O19]`.
4. **FN, major, B — SC-05 `CMP-INVENTORY:review_implementation`.** The dependency is unregistered and no
   `investigate_unknown` was raised. A found it through the prose reference in `REQ-LOW-STOCK-ALERT`.
5. **FP, B — SC-06, a spelling change in a requirement title**, produced 4 obligations:
   * `CAP-NOTIFY:review_spec` [O05];
   * `CMP-NOTIFIER:review_implementation` [O16];
   * `REQ-LOW-STOCK-ALERT:check_contract` [O16, O17];
   * `TEST-EMAIL:rerun_test` [O29].
   Every one of them comes with a valid explanation path, and every one is unnecessary.

## 6. Costs (machine proxies only)

* **Prediction volume** (scored pairs including unknown-labeled ones): A 75, B 77, C 71, A2 179.
* **Context.** A read 34,013 characters across 105 sections in total; a full rendered spec has a median of 3,635
  characters. B and C touched 98 and 90 nodes on their explanation paths.
* **Algorithm time.** The median per scenario is about 0.2 ms for A and 0.5 ms for B/C on this container (varies run to run; see `out/timing.json`). This is
  irrelevant next to human review time.
* **Curation.**
  * The two hand-curated graphs have 12/16 and 25/33 nodes/edges.
  * Scenario setup needed 5 graph edits and 6 evidence records.
  * C used 4 evidence records to remove 6 checks, one of them unsafely.
* **Not measured:** reviewer time, evidence-production time and edge-maintenance effort. This report makes no
  efficiency claim.

## 7. Answers to the handoff questions

1. **Does B recall more required checks than A?** No. B had 31 TP to A's 32, out of 54. Precision was comparable,
   and so was critical-miss severity (B 2/16 vs A 5/16). The difference of one pair is not distinguishable on 24
   curated cases. B is better on contract and multihop changes; A is better on semantic changes and on dependencies
   that exist only in prose. Maintenance cost cannot be separated, because A's document is rendered *from* the
   curated graph (see limitation 4).
2. **Does C reduce unnecessary checks without new misses?** Only partly. It removed 5 unnecessary checks and 1
   critical required one. In non-adversarial cases pruning was safe; it was unsafe in the one case designed to probe
   evidence completeness.
3. **Where do the rules fail?**
   * Implementation changes never reach tests.
   * Terminal `check_contract` stops at consumers, so the consumer's own requirements and tests are missed.
   * Reverse `blocks` links are not traversed: a requirement change does not flag its resolved question.
   * An implementation change does not flag the component's own contract.
   * Unregistered dependencies are silently missed, with no `investigate_unknown`.
   * There is no editorial/wording aspect, so wording-only edits fan out like semantic ones.
4. **Representation versus curated knowledge?** This design cannot separate them. A and B consume the same curated
   relationships, so the A-vs-B contrast isolates *directional typed rules vs undirected ID adjacency*, and that
   contrast was a wash. Two of A's wins came from knowledge present in node *text* but not in edges, which points to
   the curation gap, not to the representation.

**Thesis verdict:** H1 is *not supported*. H2 is *not supported*: pruning removed a required critical check in the
adversarial case. Overall the corpus is **insufficient to evaluate** the original thesis, for the reasons below.

## 8. Limitations (read before citing any number)

1. **Single, non-blind reviewer.** I (the agent that built the harness) wrote the oracle after reading the v0.1
   rule table, though before seeing any prediction. There was no second reviewer and no adjudication. The scenarios
   may be biased toward rule-sensitive cases. 3 of 24 scenarios were *designed* as adversarial cases for the engine.
2. **Stipulated facts.** There is no real code and no implementation replay. "Missed check" is a proxy; nothing here
   measures escaped defects.
3. **Small, curated n = 24.** No confidence intervals are given and no population-level claim is made. A one-pair
   difference is noise.
4. **The document baseline inherits graph curation.** It is rendered from the same graph, with every relationship
   written out. A real document would usually be poorer, which would favour B, or richer in prose, which would
   favour A.
5. **Labeling conventions matter.** These include "re-run tests that execute changed code", one obligation per
   target, and treating checks on test-covered requirements as discretionary. The post-hoc table in §2 shows the
   main conclusion survives dropping the first convention. The others are not stress-tested.
6. A2 and the rerun-test sensitivity are reported for context only. A2 was pre-registered as a secondary
   condition; the rerun-test sensitivity is post hoc.

## 9. Recommendation

Do **not** expand the architecture on the strength of these results. In order:

1. **Fix measurement first (cheapest, highest value).** Have a second person label the 24 scenarios blind from
   `scenarios/documents/` and `oracle/v1/*.json:ground_facts`, then report agreement. Add a held-out set of ≥ 24
   scenarios written by someone who has not read `influence.py`. The harness takes new scenarios with no code
   changes.
2. **The follow-on hypothesis most worth testing** is a *minimal, pre-registered rule addition* (handoff option ii),
   evaluated only on the new held-out set:
   * (a) implementation-aspect changes raise `rerun_test` on tests that verify the component's implemented
     requirements and constraining contracts;
   * (b) a consumer reached by a contract/provider change continues one hop to its implemented requirements and
     their tests.

   These target the two largest observed miss classes: 12 of B's 23 misses for (a), and 4 for (b) (SC-08, SC-21,
   SC-22, SC-23). Their precision cost must be measured, not assumed.
3. **Make pruning evidence declare its scope** (relates to handoff option i, contract-scoped `depends_on`). SC-14
   shows that a passing, current record does not mean a consumer's reliance was tested. Until evidence carries the
   clauses or input domain it covers, C's savings (5 checks here) do not justify its risk (1 critical miss).

Options iii–v of the handoff (obligation resolution, Git links, agents, learned weights, knowledge fabric) remain
unjustified by this evidence.
