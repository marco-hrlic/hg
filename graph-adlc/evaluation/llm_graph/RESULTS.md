# graph-adlc v0.3 — LLM-assisted graph maintenance: results

**Date:** 2026-11-03 · **Engine:** graph-adlc 0.1.0, unchanged · **Layer:** `graph_adlc/llm_graph/` · **Oracle:** v1.0, single reviewer, exploratory · **Prompts:** frozen in `prompts/PROMPTS.lock.json`

This file is generated by `evaluation/llm_graph/report.py` from `out/*/metrics.json`. Interpretation is in the sections marked *Reading*.

## Bottom line

* **A live model was evaluated: `gpt-6.1-terra` (openai), one run per arm.** The oracle, fixtures and reference graph share one author, so every live number is exploratory and single-reviewer. Section 11 has the tables and the deviations from the frozen protocol.
  * ledgerlite, E5 recall/precision: D 1.00/0.67; G0 0.25/1.00; G1 0.50/1.00; G2 0.50/1.00; H 0.50/1.00.
  * toolshare, E5 recall/precision: D 1.00/0.67; G0 0.75/1.00; G1 1.00/1.00; G2 1.00/1.00; H 1.00/1.00.
  * **Maintenance recovered the code-only dependency in both projects; construction alone did not.** G1 has no import scan, so the model added the edge itself from the code diffs. G0, built once from the initial documents, never saw it.
  * **The document-only arm D missed no critical target; the maintained graphs did (ledgerlite: REQ-CSV-EXPORT).** That miss is the engine's terminal `check_contract` rule (H misses it too), not graph quality. D's cost is lower precision: it also names entities and documents outside the labelled set.
* **What was built and verified:** an end-to-end, opt-in maintenance loop over the existing engine — source snapshots (files and immutable Git commits) → model proposal → citation/provenance validation → per-operation human review → `GraphADLC.propose`/`commit` → spec-only Markdown → influence before/after — plus a missing-edge challenge, an evidence-sufficiency gate, a live provider adapter and a deterministic scripted fake. The loop ran **5 events on one persistent graph per project and arm** for two independently written projects; all 15 acceptance cases (L01–L15) have passing tests.
* **What the deterministic parts of the scripted self-check show** (these do not depend on the fake):
  * The deterministic import scan recovered the code-only dependency in both projects (toolshare `CMP-HOLDS → CMP-NOTIFY`: recovered; ledgerlite `CMP-CSV → CMP-MONEY`: recovered), with verified line-level citations into the commit that introduced it, before the impact question was asked.
  * **SC-14 reproduced on independent material.** In ledgerlite, a `contract_preservation` record that passed, was current, and covered only amounts below 1000 lets the unchanged v0.1 engine prune CMP-CSV, CMP-PDF; the critical consumer CMP-CSV is among them. The new coverage gate refused that record (1 refused, 0 admitted), so the gated condition prunes nothing. Pruning stays off by default.
  * **Every graph arm, including the curated reference graph H, misses REQ-CSV-EXPORT.** The engine's `check_contract` on a consumer component is terminal, so a broken consumer never reaches the requirement it implements. This is the v0.2 'premature terminal propagation' class again, now on a code-discovered dependency; better graph maintenance cannot fix it.
  * Wording-only edits (scripted inputs): without the maintenance loop, the engine has no editorial aspect and raises 3 (toolshare) and 2 (ledgerlite) obligations on the reference graph. With the loop, an editorial change is either recorded as a `no_change` or held in quarantine for review instead of being committed.
* **Recommendation:** have someone other than the fixture author label the E5 impacts and repeat the live run (more than one sample) before drawing conclusions. Separately, version the engine rule that lets `check_contract` on an implementing component reach its requirement: in the live run it is the binding limit for every graph arm on ledgerlite, while arm D, which has no graph, finds that requirement.

## 7. Notable failures (case by case)

1. **ledgerlite E5: `REQ-CSV-EXPORT` missed by every arm (critical).** The path `CMP-MONEY` → (depends_on) → `CMP-CSV` ends at a terminal `check_contract`, and the rule table has no step from a checked consumer component to the requirement it implements. Source: the DR-001 criterion 'no thousands separators' versus c3 `money.py`, where `f"{q:,} {currency}"` is used by `csv_export.py`.
2. **ledgerlite E5: `TEST-MONEY-FORMAT` missed by every arm.** An implementation-aspect change to a component does not reach tests that verify its contract. The test's sample table (all < 1000) is exactly why the preservation evidence was insufficient.
3. **SC-14 recreated.** The engine pruned the critical consumer on passing, current, incomplete evidence (section 3, exploratory pruning). The v0.3 gate requires declared coverage of the change's declared input domain. Without a declared domain, nothing is admissible.
4. **Wording-only changes have no engine representation.** The safe handling is procedural (a `no_change` record or quarantine). If a reviewer accepts an editorial `update_node`, it still propagates as a semantic change.
5. **Lifecycle quirk.** `reconcile --rebase` on an `active` work unit fails ('active -> active'), so the replay rebases only invalidated units.

## 11. Live run

**Model:** `gpt-6.1-terra` via openai (`https://api.openai.com`), JSON mode on, temperature provider default, output budget 32000 tokens per call. Reviewer: `policy:conservative-v1` (not a human). Prompts unchanged (`PROMPTS.lock.json`).

### 11.1 Deviations from the frozen protocol

* **Output budget raised from 8000 to 32000 tokens** (`GADLC_LLM_MAX_TOKENS`). With 8000, every proposal call ended `finish_reason=length` with empty content, so every proposal was unparseable.
* Temperature: the model rejected `temperature=0`, so the adapter retried with the provider default and recorded that (designed behaviour, listed for completeness).
* **Two harness bugs fixed during the trial**, both crashes on paths the scripted replay never reached. Scripted outputs are byte-identical before and after. (1) The stand-in reviewer accepted an auto-generated `blocks` edge while deferring its question node; such edges are now deferred with the node. (2) On rebase, an op that a sibling proposal from the same base had already committed was re-applied; it is now dropped as a duplicate.
* **The run spans two invocations.** toolshare/D, toolshare/G0, toolshare/G1 were completed before fix (2) and reused with `--resume`, which refuses traces from a different model configuration. Fix (2) only changes rebases that contain such duplicates, and no rebase happened in those arms, so they would have run identically.
* Aborted attempts are kept, unscored, in `out/live_aborted_attempt1/`, `out/live_aborted_attempt2/`, each with an `ABORTED.md`.

### 11.7 Reading

* **RQ1 (construction).** From the initial documents alone (G0), the model found every expected entity and every required relation except the code-only one, which is not in the documents. Beyond the oracle, it added only `realized_by` artifact nodes and edges.
* **RQ2 (maintenance).** Over the 5 events, the maintained graph (G1) picked up the code-only dependency in both projects without the import scan, and recall on E5 rose to the level of the curated reference graph H in both. The validator raised no `invalid` op in any live arm, so there were no fabricated citations or silent removals. Quarantines came from contradictions, plus a few suspected duplicates (section 11.4). The model raised many contradiction questions, which costs review time.
* **RQ3 (benefit over documents only).** Not shown here. Arm D matched or beat every graph arm on recall in both projects, at roughly a tenth of the tokens, and lost only on precision. The one critical target the graphs miss (`REQ-CSV-EXPORT`) is an engine propagation limit, not a modelling failure. So on this material the graph's advantage is precision and an auditable, persistent structure, not recall.
* **Wording-only edits (E4).** In every maintained arm, the model classified the edit itself as editorial and it was recorded as `no_change`; nothing about it propagated. The obligations counted in section 11.5 come from something else: in the same step, the model raised contradiction questions about unrelated mismatches between documents and code, and their `blocks` edges raise `review_spec`. One of them (ledgerlite: the architecture says CSV amounts bypass the money formatter, but the exporter calls it) is the defect that E5 exposes. The oracle labels E4 'nothing needs re-verification', so these count as false alarms. Whether they should count is a labelling question for an independent reviewer. Toolshare G1 shows 0 because its question was deferred, not committed.
* **Caveats.** One sample per arm, one author for oracle, fixtures and H, and a policy reviewer. Treat these as hypotheses to test with independent labels and repeated runs, not as results.
